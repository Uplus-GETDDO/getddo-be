## 고민과 판단

- 기존 Redis는 숫자 키를 사용한다. 응모의 USER·EVENT 거절 상태가 한쪽만 저장되는 실패를 막기 위해 응모 전용 HASH의 단일 HSET을 선택했다. 각 구간의 논리 만료는 payload에 보존하고 비응모 키는 바꾸지 않았다.
- Lua 전체 롤백을 가정하지 않고 미활성 후보 정리와 일반 429 유지 결과를 분리했다. 자동 재집계를 피하려고 응모 전용 연결에서 자동 재전송을 끄고 EVAL을 한 번 수행한다.
- 상세 구현·설정·GD-291 인계 계약과 검증 결과는 [GD-144 구현 문서](https://github.com/Uplus-GETDDO/getddo-be/blob/6cd23b8d951a5c5161ab11b263450f5bc1d87e71/docs/02-api/entry-auto-blocking.md)에 기록했다. 공용 정책은 getddo-spec을 원본으로 유지한다.

### GD-122 관리자 추첨 이름 응답

- GD-284의 `UserNameRepository` 일괄 조회를 재사용했다. `DrawAdminNameService`에서 중복 ID와 null을 제거하고 페이지 또는 응답 단위로 한 번 조회한다. 필요한 ID가 없으면 조회하지 않는다.
- 기존 서비스의 권한·상태 검사를 통과한 결과에 현재 이름을 보충한다. 저장된 결과·후보·스냅샷·검증 입력·감사 원문과 공개 화면 마스킹은 변경하지 않았다. DB 스키마와 다른 담당 영역도 변경하지 않았다.
- 이름은 별도 저장하거나 캐시하지 않는다. 사용자 ID가 없거나 현재 이름 조회에서 사용자가 발견되지 않으면 이름은 null이다.
