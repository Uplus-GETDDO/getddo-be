- [GD-144](https://ureca4.atlassian.net/browse/GD-144), [구현 PR #159](https://github.com/Uplus-GETDDO/getddo-be/pull/159)의 Redis 책임 분리 리팩토링을 수행했다. 구현 커밋은 `2d82dce7`이다.
- `storage:redis`에 Redis 제한기·전용 연결 풀·Lua·저널 접근·Redis 빈 구성을 이동했다. 공통 인터페이스·판정·차단 모델·순수 정책과 메모리 구현은 core, HTTP 처리·사용자 검증·설정 바인딩은 api에 둔다.
- 테스트도 책임 모듈로 이동했다. 실제 API YAML 바인딩 검증은 api에 유지하고 Redis 통합 테스트는 MySQL 픽스처 의존 없이 분리했다.
- [구현·인계 문서](../../02-api/entry-auto-blocking.md#모듈별-책임)와 README의 모듈 의존 관계를 갱신했다.

## 고민과 판단

- Redis 코드를 파일만 이동하면 storage가 API의 설정·판정 타입에 역으로 의존하므로, 설정 바인딩 record는 API에 유지하고 순수 core 정책으로 변환했다. core로 이동한 일반 판정·메모리 구간은 프로젝트 관례에 맞는 불변 클래스로 정리했다.
- Lua의 한 번 평가, 연결 재전송 금지, 기존 memory/redis 선택과 사용자 정의 제한기 교체 계약을 유지했다. Redis 장애 시 메모리로 자동 전환하는 기능을 추가하지 않았다.
- Redis 클라이언트의 API 직접 의존을 제거하면서 core Service의 트랜잭션 메타데이터 해석에 필요한 Spring TX 의존성을 API에 명시했다.

## 확인 결과 / 막힌 점

- 전체 단위 테스트 1,684건 통과: api 515, core 1,062, storage:db 96, storage:redis 9, storage:s3 2. 실패·오류·건너뛰기 0건이며 모듈 이동 전 전체 건수를 유지했다.
- 아래 명령으로 전체 빌드와 API·DB·Redis 통합 테스트 소스 컴파일을 완료했다. 로컬 통합 테스트는 사용자 요청으로 실행하지 않았다.

```bash
./gradlew test build :api:compileIntegrationTestJava :storage:db:compileIntegrationTestJava \
  :storage:redis:compileIntegrationTestJava \
  -x :api:integrationTest -x :storage:db:integrationTest -x :storage:redis:integrationTest \
  --no-daemon --max-workers=1 --no-parallel
```

- API 운영 코드의 직접 Redis import 부재, core·storage:redis의 API 역참조 부재, 두 Lua 파일의 이동 전후 바이트 동일성을 확인했다. 실행 JAR에 새 Redis 모듈과 Lua가 포함되며 이전 API 경로의 중복 클래스·Lua 파일이 없음을 확인했다.
- 실제 Redis/MySQL 연결·배포 검증과 새 커밋의 원격 CI·CodeRabbit 완료 결과는 아직 확인하지 않았다. 공용 HTTP 계약·DB 스키마·마이그레이션은 변경하지 않았다.
