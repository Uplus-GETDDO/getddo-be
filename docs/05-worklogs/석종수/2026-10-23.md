## 고민과 판단

- Redis 코드를 파일만 이동하면 storage가 API의 설정·판정 타입에 역으로 의존하므로, 설정 바인딩 record는 API에 유지하고 순수 core 정책으로 변환했다. core로 이동한 일반 판정·메모리 구간은 프로젝트 관례에 맞는 불변 클래스로 정리했다.
- Lua의 한 번 평가, 연결 재전송 금지, 기존 memory/redis 선택과 사용자 정의 제한기 교체 계약을 유지했다. Redis 장애 시 메모리로 자동 전환하는 기능을 추가하지 않았다.
- Redis 클라이언트의 API 직접 의존을 제거하면서 core Service의 트랜잭션 메타데이터 해석에 필요한 Spring TX 의존성을 API에 명시했다.

## GD-291 — 고민과 판단

- 기존 작업자의 DB 행 잠금은 각 도메인 테이블에 묶여 있어 Redis 저널에 그대로 적용할 수 없었다. 동일한 스케줄링 관례를 유지하면서 저널에 건별 토큰과 임시 소유권을 추가했다. 오래된 소유자는 완료·재예약을 바꾸지 못한다.
- DB 커밋이 끝난 뒤에만 완료를 표시한다. 삽입 실패는 rollback 후 별도 트랜잭션에서 같은 PK의 모든 필드·JSON 근거를 비교하고, 다른 PK의 복합 UNIQUE 충돌이나 다른 근거는 성공으로 간주하지 않는다.
- 전체 저널이 복구 원본이다. 전역·pending·사용자 인덱스 유실, 고아 PREPARED와 원본 없는 사용자 연결을 처리하되, 손상된 ACTIVE나 만료된 미저장 원본은 삭제·재차단하지 않는다.
- 배치 실행은 전용 단일 스레드로 넘기고 프로세스 내 중복 시작을 막았다. 전용 TaskScheduler 빈을 추가해 기존 공용 스케줄러의 자동 구성을 바꾸는 방식은 사용하지 않았다.
