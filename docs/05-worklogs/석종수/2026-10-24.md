# 2026-10-24

- 상태: 검토 대기 — Codex 작성, 담당자 확인 전
- 기록 범위: 24일 부하 테스트 설계 논의. 25일에 이어서 보완한 내용은 아래 별도 항목에 구분했다.

## 오늘 한 일

- 대규모 연속 재추첨 검증을 다른 테스트 에이전트에 전달할 프롬프트로 정리했다. 응모자 1천·5천·1만·2만·3만·5만 명에서 당첨 취소와 재추첨을 50회 순차 반복하고, 매 회차 후보 명단과 과거 전체 당첨 이력을 대조하는 계획이다. 실제 테스트는 실행하지 않았다.
- 서비스 전반의 스파이크·버스트 테스트를 Locust 기준으로 정리했다. 조회와 응모·출석·게임·미션을 혼합하고, API별·시간 구간별 p50·p95·p99와 실제 RPS·오류율을 기록하도록 요청 사항을 작성했다.
- VU는 가상 사용자 수이며 요청 한 건을 뜻하지 않는다는 점을 정리했다. 반복 요청과 사용자당 1회 요청, 전체 RPS와 사용자당 요청 빈도를 구분했다.
- 요청량 중심 시험에서는 VU·대기 조건으로 부하를 만들고 실제 RPS를 측정하며, 사용자 행동을 재현하는 시험과 서버 처리 한계 측정을 구분하기로 했다.
- 출석 날짜 변경 검증의 준비 조건을 검토했다. 두 날짜의 일일 보상과 해당 월의 연속 출석 정책, 서버별 처리 근거·시간 동기화 확인이 필요하다. 클라이언트 전송 시각만으로 출석 날짜를 판정하지 않는다.

## 고민과 판단

- 단순히 당첨 결과에서 중복이 발견되지 않았다는 것만으로 재추첨 제외 규칙을 검증할 수 없다. 취소된 당첨자를 포함한 과거 전체 당첨자가 다음 회차 후보에도 없는지 확인해야 한다.
- 응모권 부족·이미 처리된 요청·429만 반복되면 정상적인 신규 업무 처리 부하를 재현하지 못한다. 신규 성공, 멱등 재조회, 업무 거절, 요청 제한, 서버 오류를 나눠 기록하도록 했다.
- 성공 응답과 거절·오류 응답의 지연을 분리하고, 구간별 백분위수를 평균 내어 전체 백분위수로 사용하지 않도록 했다.
- 사용자 수가 늘었는데 실제 RPS가 증가하지 않으면 서버 지연과 부하 발생기 자원 부족을 구분해야 한다. 서버 2대와 Locust 워커 수는 별도 조건이다.

## 확인 결과 / 막힌 점

- 이번 기록의 결과물은 테스트 시나리오와 전달용 프롬프트다. Locust 코드 작성·배포·부하 발생·DB 점검 SQL 실행·통합테스트는 수행하지 않았으며 성능 개선이나 정합성 통과를 주장하지 않는다.
- 초기 요청 비율인 보상 20%·응모 30%·조회 50%는 당시 테스트용 제안값이다. 도메인 정책이나 확정된 운영 트래픽으로 보지 않으며, 25일 후속 논의에서 고정 조건에서 제외했다.
- 스테이징의 보상 정책·유효 사용자와 게임·미션 입력, 워커 자원, 서버·DB 관측 권한 및 목표 VU 달성 여부는 실행 담당자가 확인해야 한다.
