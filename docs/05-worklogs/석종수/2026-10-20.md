## 오늘 한 일

- [GD-234](https://ureca4.atlassian.net/browse/GD-234) 추첨 후보·실행 연결 저장 방식을 비교하고, 기존 JPA 경로에 배치 100을 적용해 [PR #140](https://github.com/Uplus-GETDDO/getddo-be/pull/140)을 작성했다.
  - 후보·연결 저장 구간에만 세션 배치 크기를 지정하고 성공·실패 후 기존 설정을 복원한다. 후속 수정에서는 입력 고정·flush·재조회 전에 복원하도록 범위를 좁혔다.
  - UUID 생성, Auditing, JSON 변환과 서비스 트랜잭션은 기존 JPA 처리를 유지했다. 테이블·마이그레이션은 추가하지 않았다.
  - MySQL 드라이버의 `rewriteBatchedStatements=true` 적용 방법을 문서화했다. 공통 JDBC URL·배포 환경은 변경하지 않았다.
- 기존 JPA, 배치 50 단독, 배치 50 + 드라이버 옵션, 배치 100 + 드라이버 옵션을 비교했다. 배치 100 추가 측정은 1만·2만·5만 명만 실행했다.
- 추첨 정합성 확인 항목 14개를 정리하고 재실행, 동시 요청, 저장 실패, 마감 경합, 서버 강제 종료, 재추첨·발표를 격리된 로컬 MySQL에서 검증했다.
- 저장 성능 통합 보고서, 과거 정합성 검증 기록, 이번 장애·정합성 검증 결과를 각각 HTML로 정리했다. 보고서와 실험 원본은 로컬에 보존했으며 이 워크로그 PR에는 포함하지 않았다.
- 추첨의 Redis 적용 필요성을 검토했다. 현재 기능·정합성 요구를 위해 필수라는 근거는 찾지 못했고, 발표 결과 조회 캐시는 효과 비교 후보로만 남겼다.

## 고민과 판단

- 직접 SQL을 추가하기보다 기존 JPA 매핑을 보존하면서 저장 요청을 묶는 방법을 선택했다. 배치 100은 100개마다 커밋한다는 뜻이 아니며, 업무 트랜잭션 경계는 유지한다.
- 배치 크기만 지정한 방식은 모든 규모에서 일관되게 빨라지지 않았다. 아래 결과는 드라이버 옵션까지 적용한 측정이며, PR 코드만 반영하고 JDBC 옵션을 켜지 않으면 같은 효과를 보장할 수 없다.
- 같은 실행의 재요청과 새로운 재추첨을 구분했다. 확정된 동일 실행은 후보·조건과 당첨 결과를 재사용하고, 취소에 따른 새 재추첨은 빈 자리만 대상으로 한다.
- Redis로 기존 DB 잠금·소유권·복구 기록을 교체할 필요는 확인되지 않았다. 이전 조회 부하 실험의 지연도 로컬 자원·부하 생성기 제한이 섞여 있어 DB 조회 병목이나 Redis 필요성으로 단정하지 않았다.

## 확인 결과 / 막힌 점

### 저장 성능과 데이터 검사

아래는 명단 저장 구간의 시간이다. 두 방식 모두 드라이버 옵션을 켰다.

| 후보 인원 | JPA 배치 50 | JPA 배치 100 |
| --- | ---: | ---: |
| 1만 명 | 3.827초 | 2.035초 |
| 2만 명 | 6.544초 | 3.132초 |
| 5만 명 | 12.962초 | 9.545초 |

- 1만 명은 3회 중앙값, 2만·5만 명은 각 1회다. 배치 100의 10만 명은 측정하지 않았다. 동일 계측 JAR를 사용했지만 실행 시점·캐시·누적 데이터·호스트 부하 영향이 남아 있어 시간 차이를 배치 크기만의 효과로 단정하지 않는다.
- JPA 비교 실험 27회(본 측정 23회·예비 실행 4회) 모두 후보 수·중복 참여자·응모권 합계·가중치 합계·연결 수·당첨 수와 중복 검사에 통과했다. 이 집계 검사는 장애·동시성 테스트와 별도다.
- 초기 구현 `65bb7c73` 기준 단위테스트 1,516건과 `:api:bootJar` 패키징에 성공했다. 이를 후속 수정본 전체 빌드 성공으로 표현하지 않는다.

### 재실행·장애 정합성 검증

- 기준 코드 `7d80a8cd`의 별도 사본에서 `:core:test --tests 'com.getddo.core.drawing.*'`와 `:storage:db:integrationTest --tests 'com.getddo.db.drawing.*'`를 실행했다. 추가 테스트와 자원 설정은 사본에만 적용했다.
- 재검증 결과를 반영한 최종 건수는 단위 224건·DB 통합 119건, 합계 343건이다. 실패·오류·건너뜀은 0건이며 재실행한 같은 테스트는 중복 합산하지 않았다.
- 별도 JVM을 실제 강제 종료한 4개 지점 모두 복구·재요청 검증에 통과했다. 후보 12명·당첨 정원 5명으로 확인했다.

| 강제 종료 지점 | 종료 직후 후보 / 당첨 결과 | 복구·재요청 후 후보 / 당첨 결과 |
| --- | --- | --- |
| 후보 저장 후, 연결 저장 전 | 0 / 0 | 12 / 5 |
| 후보·조건 확정 후, 선정 전 | 12 / 0 | 12 / 5 |
| 결과 flush 후, 커밋 전 | 12 / 0 | 12 / 5 |
| 결과 커밋 후, 응답 반환 전 | 12 / 5 | 12 / 5 |

- 미완료 3건은 새 JVM에서 만료 시도 기록·재시도 대기 후 자동 실행 경로로 복구했다. 확정 결과 1건은 새 JVM에서 기존 결과를 반환했다. 각 실행은 하나만 남았고, 이후 3회 재요청에서도 저장된 후보·결과를 유지했다.
- 300초 소유권 만료와 10초 재시도 대기는 테스트 시계를 이동해 검증했다. 실제 JVM 종료·DB 롤백은 수행했지만 OS 전체 종료, DB 서버 중단, 실제 HTTP 소켓 단절이나 대규모 장애 부하는 재현하지 않았다.
- 초기 실행은 Windows 클래스 파일 조회 지연을 확인해 중단하고, 클래스 경로를 로컬 JAR로 묶어 같은 범위를 다시 실행했다. 추가 발표 테스트의 초기 상태 기대값 오류(`CLOSED` 대신 `DRAW_CONFIRMED`)와 오류 enum 참조 오타를 수정한 뒤 발표 묶음 12건을 재검증했다. 실패·중단 로그도 보존했다.
- 테스트 사본의 운영 소스 700개가 기준 커밋과 동일함을 해시로 확인했다. 기존 작업 브랜치·운영 코드·배포 서버는 변경하지 않았다. 테스트 MySQL은 실행 종료 후 정리된 것을 확인했다.
- 전체 프로젝트 테스트·전체 빌드는 실행하지 않았다. 위 건수는 추첨 관련 선택 검증과 발표 묶음 재검증의 결과다.
- 응모 마감 경계의 문서 확인 사항이 남았다. 현재 코드는 마감 전 최종 검사를 통과하고 커밋만 지연된 응모를 포함하는데, 공용 스펙은 접수 완료를 트랜잭션 확정 시점으로 정의한다. 승인된 예외·문서 반영 여부를 응모 담당자와 확인해야 하며 이번 작업에서 정책을 변경하지 않았다.
