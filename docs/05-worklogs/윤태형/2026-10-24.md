### 스테이징 서버에서 정합성 실측

스테이징(API 서버 2대, ALB 뒤)에서 Locust 시나리오로 아래 시험을 실행했다. 서버 기록(DB 기준)으로 판정했고 클라이언트 시계는 쓰지 않았다. 원자료와 Grafana 스냅샷은 별도 보관했다.

- **마감 직전 응모 폭주 3회**: 사용자 200명이 마감 10초 전부터 5초 후까지 응모 5건씩(회차당 약 1,000건)을 보냈다. 접수 510·486·526건(합계 1,522), 마감 거절(`ENTRY-005`) 504·510·464건, 응모권 부족(`TICKET-006`) 5·4·10건이었다. **마감 뒤에 확정된 응모는 3회 모두 0건**, 접수 건수·응모권 차감·사용 이력은 서로 같았고 거절 건의 사용 이력은 0이었다. 추첨 후보(192·191·193명)는 접수된 사용자와 일치했고, 마지막 접수는 마감 21~24밀리초 전이었다. 1회차는 시나리오 검증 함수 오류로 요청이 1,019건이었고 수정 뒤 2·3회차는 정확히 1,000건이다.
- **같은 사용자의 동시 요청**: 사용자 100명이 마감 90초 전에 요청 5건씩을 동시에 보냈다. 응모권 3장 60명은 전원 정확히 3건, 1장 30명은 전원 정확히 1건, 같은 키로 보낸 10명은 전원 행 1개였다. 접수 220 = 차감 220 = 사용 이력 220, 응모권은 SPENT 220 / AVAILABLE 40으로 합계가 보존됐다.
- **서버 2대 확인**: 두 서버가 요청을 거의 반반(약 49.8% : 50.2%) 처리했다. 같은 사용자의 25회 호출에서 11번째부터 429가 나와 요청 제한 카운터를 서버가 공유함을 확인했다. 이벤트 7개는 모두 추첨 1건과 시작 알림 작업 1건뿐이었다. 서버 간 시계 차이는 측정 지터(약 ±15~30밀리초)보다 크다는 증거가 없었으나 20밀리초 안팎은 구분하지 못했다.
