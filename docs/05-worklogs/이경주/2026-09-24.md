## 오늘 한 일

- UUID v7 선택의 근거를 확인하기 위해 독립 Docker MySQL에서 v4/v7 삽입 실험을 진행했다.
- 재현 도구, 원본 데이터, 그래프와 캡처를 GitHub Wiki에 정리했다.
- ADR은 UUID 버전 선택과 `updated_at` 분리라는 두 결정에 집중한다.

## 고민과 판단

UUID v4도 인덱스를 사용할 수 있다. 저장 형식을 `BINARY(16)`으로 맞추고, 무작위 키와 시간순에 가까운 키의 삽입 특성을 비교했다. 상세 결과와 근거 자료는 Wiki에서 관리한다.

## 확인 결과 / 막힌 점

- [UUID v4·v7 성능 비교 결과 — 당시 Wiki 버전](https://github.com/Uplus-GETDDO/getddo-be/wiki/MySQL-UUID-v4-v7/4ee4c216f5d2784848feade13febdb5c246f563e): 실험 환경·방법, 회차별 수치, 그래프·캡처, 원본 자료와 재현 절차.
- 10만·50만 행에서 UUID별 6회씩 총 24회 측정과 2회 워밍업을 완료했다. 이 조건에서는 v7의 삽입 시간·페이지 분할·PK 크기 중앙값이 더 작았다.
- 본 실행은 종료 코드 0으로 끝났으며, 워밍업 포함 총 7,240,000행의 행 수·UUID 버전/길이·payload 검증과 회차별 ID 왕복 조회를 통과했다.
- 최초 준비 실행의 payload 타입 오류는 수정 후 새 컨테이너에서 재실행했다. 실패 로그도 보존했다.
- 단일 JDBC 작성자와 작은 버퍼 풀에서 얻은 결과다. 운영 성능이나 JPA·Auditing·FK 매핑·시각 정밀도 검증으로 일반화하지 않는다.
- 실험·문서화에서는 제품 동작을 변경하지 않아 애플리케이션 전체 테스트·빌드를 재실행하지 않았다.
- 측정 종료 후 실험 컨테이너 두 개의 중지를 확인했고, 컨테이너·볼륨은 보존했다.

## 다음 할 일

- 보존한 실험 컨테이너·볼륨의 삭제 여부를 결정한다.
