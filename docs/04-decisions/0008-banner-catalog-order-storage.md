# ADR-0008: 최대 5개 배너의 카탈로그 잠금과 순서 저장

- 상태: 제안
- 작성자 / 날짜: Codex / 2026-10-16
- 검토자: 담당자 확인 전
- 관련 작업 기록 / PR: GD-209, [PR #110](https://github.com/Uplus-GETDDO/getddo-be/pull/110)
- 대체한 ADR / 대체된 ADR: 해당 없음

## 배경

V006의 배너 순서는 CHECK(1~5)와 UNIQUE다. 다섯 자리가 모두 찼을 때 순서 교환을 임시 0·6으로 우회할 수 없다. 빈 목록에서는 배너 행 잠금만으로 동시 첫 등록을 직렬화할 수 없다.

## 결정과 이유

V028의 고정 카탈로그 제어 행 하나를 FOR UPDATE로 잠근다. 이벤트 연결이 필요한 등록·수정은 기존 이벤트 상태 잠금 후 카탈로그를 잠근다. 순서가 달라지는 배너만 같은 트랜잭션에서 제거·동일 ID로 재삽입하며 ID·생성 시각·기존 URL·키·이벤트 연결을 보존한다. 변경된 순서의 수정 시각만 Service의 공통 시계로 갱신한다. 기존 FK·CHECK·UNIQUE를 약하게 만들지 않는다.

최대 5행이므로 순서 쓰기를 직렬화한다. 공개 목록은 단일 JOIN SELECT로 읽어 미연결·논리 삭제·취소 이벤트를 숨긴다. 감사 저장 실패를 포함해 재삽입·업무 변경 전체가 롤백된다. Hibernate의 1차 캐시는 배너 Entity만 분리하며 다른 업무 Entity를 clear하지 않는다.

## 검토한 대안

- 임시 순서 0·6 사용: 기존 CHECK를 위반한다.
- UNIQUE/CHECK 제거: 사용자에게 확정한 최대 개수·순서 제약을 DB에서 잃는다.
- 기존 배너 행만 잠금: 빈 목록 첫 등록을 직렬화하지 못한다.

## 영향과 재검토 조건

현재 banners를 참조하는 외래 키는 없다. 향후 외부 FK·삭제 트리거가 추가되거나 최대 개수·쓰기량이 변경되면 이 저장 전략을 재검토한다. 실제 MySQL 순서 교환·경쟁·롤백·이전 데이터 테스트의 사용자 로컬 실행 XML을 확인했고, PR #110의 기존 head28e4ed05에서 CI 빌드·테스트와 이미지 빌드도 성공했다. 이후 리뷰 수정 커밋의 CI는 별도로 확인한다. 에이전트는 이번 수정에서 테스트·빌드를 실행하지 않았다. 운영 DB의 이전 행 유무와 이미지 실주소는 미확인이다. 공용 정책은 spec을 따른다.
