# 추첨 명단 저장 배치

- 상태: 검토 대기 · GD-234, GD-368
- 구현: 기존 JPA 저장에 세션 배치 100을 적용한다. MySQL 드라이버 묶음 전송은 접속 설정에서 활성화한다.

## 변경 범위

`DrawSnapshotRepositoryImpl.saveInput`의 최초 후보·실행별 연결 저장에 Hibernate 세션 배치 크기 100을 지정한다. 두 저장 호출이 끝나거나 실패하면 `finally`에서 이전 값으로 복원한다. 입력 고정·flush·재조회는 복원 후 실행한다. `null`은 전역 기본 설정 상속이므로 그대로 복원한다.

GD-368은 `saveRegisteredReplacement`의 실행별 후보 연결 `saveAllAndFlush` 구간에도 같은 배치 100과 `finally` 복원을 적용한다. 기존 후보의 최초 실행 소속을 확인한 뒤 배치를 설정하며, 입력 고정·후속 flush·재조회 전에는 기존 설정으로 복원한다. 최초 후보 상세를 새로 저장하지 않고, 빈 후보도 기존 재추첨 입력 고정 흐름을 따른다.

후보·연결은 기존 `saveAllAndFlush`로 저장한다. UUID v7·감사 시각·JSON 매핑은 기존 Entity/JPA 처리를 사용한다. 입력 고정과 실제 DB 정밀도로 재조회하는 흐름, 서비스 트랜잭션·잠금 순서·실패 전파·재추첨 후보 재사용은 변경하지 않는다. 100은 JDBC 배치 크기이며 커밋 단위가 아니다.

직접 SQL INSERT helper, 새 테이블·마이그레이션, 전역 `hibernate.jdbc.batch_size`는 추가하지 않는다.

## MySQL 드라이버 활성화

실제 SQL 묶음 전송에는 기존 MySQL 접속 URL의 `rewriteBatchedStatements=true`가 필요하다. 배치 크기 설정만으로 동일한 성능 개선이 보장되지 않는다.

- 로컬/IDE: 실행 환경의 `SPRING_DATASOURCE_URL`에 옵션을 추가한다. 예: `jdbc:mysql://localhost:3306/getddo?rewriteBatchedStatements=true`.
- 기존 URL에 쿼리 옵션이 있으면 `&rewriteBatchedStatements=true`를 붙인다. 중복 옵션을 만들지 않고 기존 값이 있으면 수정한다.
- RDS 파라미터 그룹을 변경하는 설정이 아니다. 배포 담당자가 관리하는 기존 접속 URL에서 활성화하며 TLS·인증서·시간대 등 다른 옵션은 유지한다.
- 이 PR은 공용 접속 URL·Parameter Store·배포 파일을 수정하거나 재배포하지 않는다. 드라이버 옵션은 같은 연결을 쓰는 다른 JDBC 배치에도 영향을 줄 수 있어 배포 담당자와 적용 범위를 확인한다.
- 비활성화하려면 접속 URL에서 옵션을 제거하거나 false로 변경하고 앱을 재시작한다. 이 경우 JPA 배치 크기 100 자체는 유지된다.

## 로컬 관측 결과

아래는 동일한 계측 JAR(c6287fb8)을 사용한 명단 저장 구간의 초 단위 관측값이다. Hibernate 7.4.5.Final / Connector/J 9.7.0, 힙 768MiB, Hikari 10, MySQL CPU 1.5·메모리 1GiB를 사용했다.

| 인원 | 기존 JPA | 배치 50 | 배치 50 + 드라이버 옵션 | 배치 100 + 드라이버 옵션 |
| --- | ---: | ---: | ---: | ---: |
| 1만 | 25.837 | 17.793 | 3.827 | 2.035 |
| 2만 | 47.019 | 39.235 | 6.544 | 3.132 |
| 5만 | 120.579 | 87.134 | 12.962 | 9.545 |
| 10만 | 192.729 | 204.618 | 25.317 | 미측정 |

1만 명은 각 3회 중앙값, 다른 규모는 각 1회다. 데이터 준비와 스케줄러 대기는 위 저장 시간에서 제외했다. 실행 순서를 섞지 않았고 DB를 재사용해 캐시·누적 데이터·공유 호스트 영향이 남는다. 성능 차이 전부를 설정 하나의 효과로 확정하지 않으며 운영 처리량을 뜻하지 않는다. 이번 PR의 최신 dev 기반 구현을 다시 벤치마크한 수치도 아니다.

1만 명의 후보·연결 INSERT는 기존/배치 50 각각 20,000회, 배치 50+옵션 400회, 배치 100+옵션 200회였다. 배치 100은 2만 명 400회·5만 명 1,000회였다. JPA 조합 실험 총 27회(예비 실행 포함)는 후보·장수·가중치·연결·당첨자 중복 검사를 통과했고 실패·재시도는 없었다. 10만 명의 배치 100은 사용자 지시로 실행하지 않았다.

최초 직접 SQL 100행 실험은 다른 기준 커밋·DB 상태에서 수행했다. 1만·5만·10만 명 저장 1.818·8.225·39.453초를 관측했지만 이번 JPA 결과와 직접 우열을 확정하지 않는다. 시각 불연속이 있었던 최초 10만 명 쌍은 비교에서 제외하고 승인 후 재측정 수치를 사용했다.

## 검증 경계

단위 테스트는 배치 100 적용 범위, 성공/실패 시 이전 세션 설정 복원과 예외 전파를 검증한다. 실제 DB 롤백·제약·드라이버 오류 처리를 증명하는 테스트는 아니다. 성능 실험의 정상 완료·수량 검사와 장애 복구 검증도 구분한다. 사용자 지시에 따라 이번 구현의 통합테스트는 실행하지 않는다.

GD-368의 재추첨 변경도 사용자 요청으로 DB 통합 테스트·성능 실험을 실행하지 않는다. 위 로컬 관측값은 과거 최초 추첨 저장 실험이며 재추첨 배치의 개선 수치가 아니다. 실제 배포의 드라이버 옵션·SQL 묶음 전송·롤백·성능 효과는 후속 확인 대상이다. 이번 변경에서 접속 URL·배포 설정을 수정하지 않는다.
