## A — 이경주: 인프라·공통 기반·사용자

- 서버와 데이터베이스 구성 및 배포
- Docker 기반 개발·배포 실행 환경 통일
- 빌드·테스트·배포 CI/CD 구성
- 도메인·HTTPS 인증서 설정
- DB 비밀번호와 인증 키 등 환경변수·시크릿 관리
- 로그·모니터링과 DB 백업·복구 구성
- 가상 사용자, 사용자 역할, 관리자 권한 및 멤버십 등급 관리
- 공통 오류 코드와 응답 형식 관리
- 각 기능 담당자가 변경 이력을 기록할 수 있는 감사 로그 기반 제공

## B — 석종수: 어뷰징 차단 기록·추첨

- 응모·보상 기록의 의심 패턴 탐지와 근거 기록
- 응모권 지급 전 차단 기록과 관리자 조회 API 구현
- 차단 사유, 발생 시각, 관련 요청과 검증 근거 기록. 구체적인 차단 범위·판정 기준은 공용 후속 확인을 따름
- 유효 응모자·응모권 수·가중치·조건의 추첨 실행별 스냅샷 보관
- 일반 가중치·차등 가중치 추첨 구현
- [공용 추첨 정책](https://github.com/Uplus-GETDDO/getddo-spec/blob/main/02-domain/drawing.md)에 따라 응모권 사용 여부와 관계없이 마감 후 5분 최초 자동 추첨 구현. 어뷰징 검토 완료·제외 판단을 선행 조건으로 요구하지 않으며 재추첨은 관리자 수동 실행
- 이벤트 내 동일 사용자의 중복 당첨 방지
- 동일 추첨 실행의 중복 요청·재시도에도 하나의 결과만 확정
- 저장된 스냅샷·알고리즘 버전·확정 결과를 이용한 정합성 검증
- 당첨 취소 사유와 재추첨 이력 기록 및 최초 추첨과의 연결
- 결과 발표 처리, 발표 전 비공개, 공개 결과 마스킹
- 결과 발표·당첨 취소·재추첨 결과를 C의 알림 기능과 연동

새로운 재추첨은 이전과 다른 결과를 만들 수 있다. 검증은 이미 확정된 동일 실행의 결과를 다시 추첨해 재현하는 것이 아니라 저장된 스냅샷과 확정 결과의 정합성을 확인하는 의미다.

## C — 전민규: 백오피스·알림·게임

- 사용자·이벤트·응모·운영 내역의 관리자 통합 조회·검색·필터
- A의 사용자·권한 기능을 이용한 관리자 사용자 조회 API. [공용 구현 범위](https://github.com/GETDDO/getddo-spec/blob/main/00-requirements/scope.md)에 따라 사용자 정보 수정은 제공하지 않음
- 배너 등록·조회·수정·삭제와 노출 순서 관리
- 출석·미션·게임·보상 정책 설정 관리자 API
- 출석·미션 정책 검증·저장·적용을 D의 기능과 연동
- [공용 게임 API](https://github.com/GETDDO/getddo-spec/blob/main/05-api/game.md)에 따라 게임 사용자·관리자 API, 게임 규칙·서버 결과 판정·점수 기록·통계와 사용자별·게임별 일일 보상 자격 처리
- 게임 보상 자격 판정 결과를 D의 실제 응모권 지급 기능과 연동하고, 지급 전 차단 기록은 B의 기능과 연동
- 부정 획득분을 포함한 응모권 회수 API·처리·알림은 [공용 응모권 규칙](https://github.com/GETDDO/getddo-spec/blob/main/02-domain/ticket.md#응모권-회수-제외)에 따라 이번 버전에서 제외
- 각 업무의 감사 기록 연동 확인. 공통 감사 검색·목록·상세 API(AU01/AU02)와 전용 조회 화면은 이번 버전에서 제외
- 사용자별 알림 목록, 읽음 여부, 개별 읽음·전체 읽음 처리
- 별도 신청 없이 이벤트 응모 자격을 충족한 사용자를 대상으로 시작 알림 생성
- 결과 발표, 일정 변경·취소, 취소 반환, 당첨 취소·재추첨 결과 알림 연동
- 비동기 알림의 중복 생성 방지, 실패 재시도, 최종 실패 조회·재처리
- 외부 문자·메일 대신 모의 발송 결과 기록

## D — 윤태형: 응모권·일회성 미션·출석·응모

- 보상 응모권 지급과 이벤트 응모 비용 차감
- 응모권 지급·차감의 사유와 원본 행위 기록
- 이벤트 취소 시 원본 이력에 연결한 응모권 반환과 잔액·이력 반영. 참여·추첨 제외에 따른 반환은 제공하지 않음
- 응모권 만료 및 잔액 반영
- 응모권 잔액과 지급·차감·반환·만료 이력 조회
- 응모권 중복 지급·반환과 보유량 초과 차감 방지
- 일회성 미션 완료 조건 검증, 달성 기록과 중복 보상 방지
- C의 게임 보상 자격 판정 결과에 따른 실제 응모권 지급과 지급 이력 기록
- 출석·미션·응모권 보상 정책의 검증·저장·적용
- [공용 출석 정책](https://github.com/GETDDO/getddo-spec/blob/main/02-domain/attendance.md)에 따라 사용자별 일일 출석 기록과 KST 날짜 기준 중복 출석 방지
- 출석 기록과 응모권 지급의 트랜잭션 일관성 보장
- 이벤트 상태·기간·멤버십·역할·응모 횟수에 따른 응모 자격·마감 검증
- 응모권 미사용·사용 이벤트 응모와 가중치 적용 이벤트의 추가 응모 처리
- 응모 기록·응모권 차감·차감 이력의 트랜잭션 일관성과 중복 요청 방지
- 이벤트별 내 응모 내역·차감 수량·처리 상태 조회와 B의 당첨 결과 연결
- 중복을 제거한 응모자 수, 총 차감 응모권 수와 본인 차감 수량 집계
- 응모권 반환 완료 결과를 C의 알림 기능과 연동

## E — 박지훈: 기본 이벤트 CRUD·취소

- 이벤트 제목·설명·이미지·응모 기간 등 기본 정보 등록
- 사용자·관리자용 이벤트 목록과 상세 조회
- 시작 전 수정과 진행 상태별 수정 제한 적용
- 시작 전이고 응모 이력이 없는 이벤트의 삭제 조건 검증
- 경품명·설명·이미지·등수·당첨 인원 관리
- 멤버십 최소 등급, 이벤트 유형, 가중치 적용 여부와 응모 제한 저장
- 이벤트·경품 CRUD의 관리자 API와 핵심 로직 구현
- GD-203의 시작·마감 상태 전환 워커와 등록·수정의 공통 감사 기록 연동. 추첨·공개 상태 연결은 B가 담당한다.
- 이벤트 취소 운영 API·취소 상태 저장과 D의 응모권 반환, C의 취소 안내, A의 감사 기록 연동. 2026-10-15 사용자 결정으로 C에서 이관한 GD-202 범위다.

## 담당 경계

### 사용자·권한 관리

- A는 사용자·역할·멤버십 모델과 인증·권한 처리를 담당한다.
- C는 관리자 사용자 조회·관리 API를 담당한다.
- D는 응모 시 사용자 자격을 확인한다.
- C는 시작 알림 생성 시 사용자 자격을 확인한다.

### 이벤트 설정과 응모 조건 검증

- E는 이벤트 기간·경품·응모 조건 설정과 저장을 담당한다.
- D는 실제 출석·응모 요청에 조건을 적용하고 검증한다.
- B는 확정된 추첨 정책에 따라 대상 확정과 추첨을 수행한다.

### 출석·응모와 응모권 처리

- D가 전체 흐름을 담당한다.
- 출석 기록과 응모권 지급은 함께 성공하거나 함께 취소한다.
- 응모 기록과 응모권 차감도 함께 성공하거나 함께 취소한다.
- C는 관리자 조회에 필요한 데이터를 연결하며 출석·응모 핵심 로직을 중복 구현하지 않는다.

### 지급 전 차단 기록·이벤트 취소 반환

- C는 게임 플레이·판정·점수·보상 자격 기록을 저장하고, D는 출석·미션·응모·응모권 지급 기록을 저장한다.
- B는 지급 전 차단 사유·발생 시각·관련 요청·검증 근거를 보관하고 관리자 조회를 제공한다.
- 게임 결과 검증·보상 자격은 C, 실제 응모권 지급은 D가 담당하며 차단 기록의 연결 계약을 B와 합의한다.
- 정상 접수된 응모를 차단 기록으로 추첨에서 제외하지 않는다. 참여 허용·추첨 제외 결정과 그에 따른 반환은 제공하지 않는다.
- 회수 대상 조회·회수 요청·처리·회수 알림은 이번 버전에서 제외한다.
- D는 이벤트 취소 시 차감 응모권 반환 정책을 검증하고 잔액과 이력을 처리한다.
- C는 처리 완료 알림을 생성한다.

### 추첨·결과 발표

- B는 추첨 대상 확정부터 추첨·검증·발표·당첨 취소·재추첨과 관련 관리자 API까지 담당한다.
- C는 B의 발표·당첨 취소·공개 명단 변경 결과를 받아 알림을 생성한다.
- 알림 생성 실패로 확정된 추첨 결과가 변경되지 않도록 한다.

### 이벤트 취소

- E는 운영 API와 취소 상태·시각 저장, 반환·취소 안내·감사 기록의 트랜잭션 연결을 처리한다.
- D는 취소된 이벤트의 응모를 차단하고 차감 응모권을 반환한다.
- B는 변경된 상태에 따라 추첨 실행을 차단한다.
- C는 상태 변경 알림을 생성한다.
- 취소와 대상 응모권 반환은 함께 완료하며 실패하면 둘 다 완료로 처리하지 않는다. 이벤트 일시 중단·재개는 제공하지 않는다.

### 출석·미션·게임·보상 정책

- C는 관리자 정책 설정 API를 담당한다.
- C는 게임 규칙·결과·점수·통계와 게임별 일일 보상 자격을 처리한다.
- D는 출석·미션·응모권 보상 정책 검증·저장·적용과 사용자 수행·실제 응모권 지급을 담당한다.
- E는 이벤트 자체의 응모 조건 설정을 별도로 담당한다.

### 알림

- C는 공통 알림 기능과 이벤트 시작 알림 생성을 담당한다.
- B는 발표·당첨 취소·공개 명단 변경 발생 사실을 전달한다.
- D는 이벤트 취소에 따른 반환 완료 사실을 전달한다.
- E는 이벤트 일정 변경·삭제·취소 시 C의 시작 알림 처리와 취소 안내 등록을 연동한다.
- A는 인증·권한 및 로그·모니터링 기반을 지원한다.

### 감사 로그

- A는 공통 기록 기반을 제공한다.
- 각 담당자는 자신의 기능에서 발생한 변경 내역을 기록한다.
- [공용 감사 기록 명세](https://github.com/Uplus-GETDDO/getddo-spec/blob/main/05-api/audit.md)에 따라 공통 감사 로그 검색·목록·상세 API(AU01/AU02)와 전용 조회 화면은 2026-10-15 사용자 결정으로 이번 버전에서 제외한다. 각 기능의 감사 기록과 기존 테이블·데이터는 유지하며, 개별 업무의 운영 내역 조회는 해당 업무 계약을 따른다.

## 운영 원칙

- 백오피스는 관리자 API를 의미한다.
- C가 모든 관리자 기능을 구현하지 않는다. 이벤트 CRUD는 E가, 어뷰징 검토·추첨·발표는 B가 관리자 API까지 담당한다.
- 담당자는 주 구현 책임을 나타내며 다른 담당자의 코드 변경이나 리뷰를 금지하는 소유권을 의미하지 않는다.
- 공용 요구사항이나 도메인 정책과 이 문서가 충돌하면 `getddo-spec`의 확정 문서를 우선한다.
