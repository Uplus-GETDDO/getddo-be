# 검증 결과 관리

정합성·동시성·장애 복구·부하 검증의 실제 결과를 실행 조건과 근거 파일로 정리합니다. 검증 계획이나 테스트 코드의 존재를 실행 결과로 기록하지 않습니다.

## 문서와 원본의 역할

| 위치 | 기록할 내용 |
| --- | --- |
| 루트 README | 대표 검증의 요약과 상세 결과 문서 링크 |
| 이 폴더의 보고서 | 실행 조건, 기대·실제 결과, 데이터 대조, 한계와 후속 조치 |
| 실행 산출물 | 테스트 HTML·XML, 대조 결과, 부하 지표·필요한 로그 |
| Wiki | 발표·시연 설명과 상세 보고서 링크; 같은 결과를 중복 관리하지 않음 |

이 안내와 템플릿의 추가 자체는 실제 기능·부하 검증 완료를 뜻하지 않습니다. 과거 README·Wiki 결과는 해당 실행의 범위를 따릅니다.

## 결과 작성 순서

1. [검증 결과 양식](../templates/verification-report.md)을 복사해 `reports/` 아래에 결과 파일을 만듭니다. 해당 폴더는 첫 보고서를 추가할 때 생성합니다.
2. 관련 기능의 공용 계약을 연결하고 검증 범위·기대 결과를 먼저 적습니다.
3. 단위·실제 MySQL 통합·통제된 동시성·HTTP·장애·부하 중 실행 방식을 구분합니다. 동시성·실패 시점의 재현을 먼저 확인하고 부하로 확대합니다.
4. 실제 실행 환경·명령·데이터 준비 방법·대조 시점을 기록합니다.
5. 시나리오별 실제 결과와 판정, 독립적인 DB 대조 결과를 작성합니다. 미실행·판정 불가 이유도 남깁니다.
6. 근거 파일을 보관하고 보고서에서 연결합니다. README·Wiki에는 필요한 요약과 상세 보고서 링크를 연결합니다.

사용자 요청에 따라 양식에는 문서 상태·코드 커밋·실행자·CI 링크 입력란을 두지 않습니다. 시나리오별 판정과 실행 일시·시간대, 실제 실행 조건·근거는 기록합니다.

## 보고서 위치와 이름

```text
docs/
├── 07-verification/
│   ├── README.md
│   └── reports/                          # 첫 실제 보고서 작성 시 생성
│       └── YYYY-MM-DD-주제.md
└── templates/
    └── verification-report.md
```

파일명 예: `YYYY-MM-DD-entry-concurrency.md`, `YYYY-MM-DD-draw-recovery.md`.

같은 날 다른 실행을 별도 보존해야 하면 `YYYY-MM-DD-주제-02.md`처럼 구분합니다. 실패 기록을 성공 기록으로 덮어쓰지 말고 재검증 결과와 연결합니다. 검증 보고서는 업무 일지와 목적이 다르며, 워크로그를 이 폴더로 옮기거나 기능 PR에 함께 넣는 방식으로 사용하지 않습니다.

## 실행 산출물 보관

현재 Gradle의 모듈별 생성 위치는 다음과 같습니다. 각 태스크를 실행한 뒤 생성 여부를 확인합니다.

| 태스크 | HTML 보고서 | XML 결과 |
| --- | --- | --- |
| `test` | `<모듈>/build/reports/tests/test/index.html` | `<모듈>/build/test-results/test/` |
| `integrationTest` | `<모듈>/build/reports/tests/integrationTest/index.html` | `<모듈>/build/test-results/integrationTest/` |

`integrationTest`는 현재 `api`, `storage/db` 모듈에 구성되어 있습니다. 실행 환경·Docker와 테스트 범위는 [루트 실행 안내](../../README.md#테스트와-ci)를 확인합니다.

자동 생성 HTML·XML·대용량 부하 원본은 Git에 일괄 추가하지 않습니다. 실제 실행에서 선택한 아티팩트·첨부 보관 위치를 보고서에 적고, 팀원이 열 수 있는지와 보관 만료 여부를 확인합니다. 현재 빌드 워크플로는 실패 시 테스트 보고서를 7일 보관하므로 성공 결과의 자동 업로드나 영구 보관을 전제하지 않습니다. 이 문서 추가로 워크플로를 변경하지 않습니다.

정합성 대조를 수행했다면 대상 수·불일치 수와 실제 검사 쿼리·assertion 위치를 남깁니다. 필요할 때 요약 JSON·CSV를 함께 보관합니다. 이 문서는 해당 파일을 생성하는 자동화나 부하 스크립트를 제공하지 않습니다.

근거에는 테스트용 식별자를 사용하고 비밀값·개인정보를 포함하지 않습니다.

## 결과 해석 기준

- `통과 / 실패 / 미실행 / 판정 불가`를 구분합니다. 검사 대상이 0건인 결과를 정상 검증으로 표현하지 않습니다.
- 실제 MySQL 연결 검증과 테스트 대역 검증을 구분합니다.
- 응답 유실·시간 초과가 발생해도 DB에는 커밋됐을 수 있으므로 재조회·재시도로 실제 결과를 확인합니다.
- 신규 처리·기존 결과 반환·업무 거절·예상 외 오류를 나눠 집계합니다.
- 잔액·이력 대조에는 동일 기준 시각·만료 조건을 적용하고, 쓰기 중 여러 API를 조회한 시점 차이를 구분합니다.
- 유효 응모자와 후보는 인원수뿐 아니라 집합 자체를 비교합니다. 추첨 결과의 사후 정합성 검증과 난수 과정의 재현은 구분합니다.
- 부하 테스트는 실제 측정 조건·지연·처리량과 사후 불일치 건수를 함께 기록합니다. 아직 정하지 않은 목표 성능을 임의로 합격 기준으로 삼지 않습니다.
- 기능 테스트 성공을 부하 성능·운영 환경·FE 전체 연동 성공으로 확대하지 않습니다.
