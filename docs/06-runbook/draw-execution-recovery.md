# 추첨 실행 실패 확인·동일 실행 재개

- 상태: 검토 대기, GD-87 구현·검증 단계
- 기준: [실행 저장 설계](../03-database/drawing-selection-storage.md#gd-87-공통-실행실패재개--구현과-검증)
- 임시 MySQL 통합 테스트에서 실패·재개 동작을 검증했다. 운영 DB 적용·운영 복구 검증은 수행하지 않았다.
- 문서 재확인: spec 원격 `7978d25`, 백엔드 원격 dev `0a32422`(2026-10-12). 최초 재개 경로는 이 대화에서 승인한 구현 계약이며 승인된 경로·권한·상태 코드는 공용 spec main `7978d25`에 게시했다. 다른 추첨 API 상세 계약은 검토 대기다. 알림의 최종 실패 복구 조건과 별개로 GD-87의 허용 상태를 따른다.

실패 확인은 실행 ID에 연결된 `draw_failures`의 코드·시각·횟수를 기준으로 한다. 실패 코드만으로 관리자 문구를 구성하며 원문 예외를 저장하거나 반환하지 않는다. 상세 조회 API는 GD-137 계약과 연결한다.

1. 실행의 현재 상태와 입력 고정 여부, 최근 실패·횟수 및 retry_at을 확인한다. CONFIRMED는 저장 결과를 유지하고 다시 선정하지 않는다. NO_ENTRIES·과거 NO_CANDIDATES는 재개 대상이 아니다.
2. FAILED에 retry_at이 있으면 예약된 자동 재시도다. 없으면 운영자 대기다. 정합성 오류·미분류 오류는 원인부터 확인하며 입력·결과를 임의 보정하거나 새 재추첨을 만들지 않는다.
3. 저장된 입력의 정합성 문제가 원인이면 해당 스냅샷을 다시 계산해 덮어쓰지 않는다. 입력 고정 전 실패이면 등록된 같은 실행을 종류별 준비 기능으로 재개한다. GD-138의 `DrawReplacementInputPreparation`은 연결되어 있다. 종류별 준비 Bean이 없거나 중복 등록된 장애는 운영자 대기이며 자동 실행으로 우회하지 않는다.
4. 최초 실행은 활성 관리자 문맥으로 POST /api/v1/admin/draws/{runId}/resume을 호출한다. 요청 본문은 없다. 재추첨은 GD-138 AD09에서 연결된 같은 runId를 사용한다. 취소·새 실행을 중복 생성하지 않는다.
5. 확정이면 200, 미확정이면 202다. 비관리자는 403, 실행 종류·상태·이벤트가 재개 불가하면 409다. 202는 확정 성공을 뜻하지 않는다. 진행 중·실패 응답 뒤에는 같은 실행을 조회한다.
6. 감사 이력의 DRAW_RESUME과 실제 처리자·시도를 확인한다. 실패 횟수는 재개해도 누적 이력에서 유지하며 새 복구 구간의 자동 재시도는 최대 3회다.

등록 커밋 후 시작 요청 전에 중단된 PREPARING/READY는 워커가 같은 실행을 시작한다. 새 실행을 등록하지 않는다. 처리 중 프로세스 중단 시에는 소유권 만료를 확인한다. 임대가 만료됐어도 실제 트랜잭션이 이벤트 잠금을 보유하면 복구는 그 종료를 기다린다. 이벤트 → 실행 잠금 아래 토큰을 재확인한 후 같은 시도를 INTERRUPTED로 한 번 기록하고 제한된 예약 또는 운영자 대기로 이동한다. 과거 RUNNING에 토큰이 없으면 자동 재선정하지 않는다.

재시도 워커를 중지할 때는 getddo.drawing.retry-worker.enabled=false를 사용한다. 중지해도 DB의 예약·실패 이력은 남는다. GD-86의 신규 이벤트 자동 시작과 별개 설정이며, 중지·재시작으로 운영자 대기를 해제하지 않는다.

## GD-86 최초 자동 등록

`DrawInitialWorker`는 마감 +1분이 지난 SCHEDULED/OPEN/CLOSED·미삭제 이벤트 중 INITIAL/0 실행이 없는 이벤트 ID를 종료 시각·ID 순으로 최대 20건 조회한다. 이벤트별 등록을 커밋한 뒤 기존 실행 서비스를 순차 호출한다. 이벤트 잠금 아래 마감·삭제·취소 조건을 다시 확인하고, 동시 등록은 기존 최초 실행을 재사용한다. 등록 이후 복구는 위의 기존 재시도 워커 계약을 따른다.

미래 시작으로 등록한 이벤트는 시간이 지나도 저장 상태가 SCHEDULED로 남을 수 있다. 추첨은 이 상태도 마감 +1분 이후에 처리하며, 시작·마감 상태 전환 작업을 선행 조건으로 요구하지 않는다.

- `getddo.drawing.initial-worker.enabled=false`: 신규 최초 실행 자동 등록을 중지한다. 기존 실행 복구 설정과 별개다.
- `getddo.drawing.initial-worker.poll-delay`: 폴링 완료 후 다음 조회까지의 밀리초. 기본 10000(10초)이며 정확한 추첨 시작 시각이나 최대 지연을 보장하지 않는다.
- 최초 선정 결과와 DRAW_CONFIRMED, 응모자 없음 실행과 NO_ENTRANTS는 각각 같은 업무 트랜잭션에서 기존 EventStatusChangeService로 저장한다. 확정 재요청은 이벤트 상태를 다시 변경하지 않는다.
- 자동 공개·공개 재호출은 제공하지 않는다. 관리자 확인·수동 공개는 GD-199, 사용자 조회의 전체 흐름 검증은 GD-140과 합류한다.
- 조회는 후보·경품을 적재하지 않지만 이벤트의 종료 시각 탐색 인덱스는 현재 마이그레이션에 없다. V2 인덱스 개선은 GD-178 후속이며 실제 실행 계획·운영 규모의 지연은 아직 측정하지 않았다.

## GD-268: 최초 자동 추첨 대기 시간 단축

최초 자동 추첨 기준을 마감 후 5분에서 1분으로 변경했다. 관리자 이벤트 응답의 `drawScheduledAt`도 `endsAt + 1분`이다. 이 시각은 대상이 되는 최소 시각이며, 10초 확인 주기·앞선 이벤트의 순차 처리·장애 복구에 따라 실제 실행은 늦을 수 있다. 결과 발표는 관리자 수동 요청으로 처리한다.

별도 데이터 마이그레이션은 없다. 배포 시 미실행 이벤트부터 새 기준으로 처리하며 이미 확정된 실행·결과는 재추첨하지 않는다. 실행 임대 5분과 기존 재시도 제한은 유지한다. 공용 정책은 [추첨 규칙](https://github.com/Uplus-GETDDO/getddo-spec/blob/main/02-domain/drawing.md)을 따른다.
