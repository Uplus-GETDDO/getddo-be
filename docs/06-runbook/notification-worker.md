# 알림 작업 처리·장애 확인

GD-68 기반과 GD-69 시작 생산자, GD-70 변경·취소 알림의 내부 실행 방식과 확인 절차다. 공용 정책의 원본은 [알림 도메인 규칙](https://github.com/GETDDO/getddo-spec/blob/main/02-domain/notification.md)이다.

## 등록과 실행

- 호출 담당자는 실제로 확정할 발생 사실의 식별키·수신자 UUID 목록·문구를 `NotificationJobRequest`로 전달한다. 수신 자격과 실제 발생 여부는 호출 담당자가 판정하며, 작업 등록은 `NotificationJobService.register()`로 한다.
- 등록은 호출자의 트랜잭션에 참여한다. 업무 변경과 작업 등록을 함께 처리하려면 호출자의 Service도 트랜잭션을 열어야 한다. 원본 업무를 롤백하면 알림 작업도 롤백된다.
- 식별키는 전역에서 발생 건을 구분한다. 같은 키·같은 입력은 기존 ID를 반환하며 다른 입력은 `NOTIFICATION-004`로 거절한다. 수신자 순서·중복과 시각의 마이크로초 정밀도는 정규화한다.
- 내부 `payload` 버전 1에 제목·내용·링크·수신자 UUID 목록과 선택 발표 ID(`publicationId`)를 저장한다. GD-93 초기 스키마에서 `publication_id`·`target_user_id` 컬럼이 제거됐으므로 발표 ID는 payload에 보존하고 수신자는 저장된 목록으로 처리한다. 이전 payload에 발표 ID가 없으면 null로 읽는다. 재시도에서는 저장된 대상을 사용한다. 이벤트 시작 알림은 생성 시점에 수신 자격을 판정한 후 등록하며, 등록 시점의 목록을 예약 대상처럼 미리 고정하지 않는다.
- `NotificationWorker`는 한 번의 폴링에서 시작 작업 등록·사용자별 생성 작업·모의 발송을 각각 최대 20건 처리한다. 기본 간격은 이전 폴링 종료 후 1초다. 동기 HTTP 요청 안에서 알림 전체 생성을 기다리지 않는다.
- `getddo.notification.worker.enabled=false`로 이 워커만 중지할 수 있다. `getddo.notification.worker.poll-delay`는 조회 주기(밀리초)이며 기본값은 `1000`이다. 기존 YAML 파일은 변경하지 않았다.
- 배포 시 V014 인덱스와 GD-72의 V021 복구 구간 마이그레이션을 적용한다. 과거 사용 후 제거된 V012·V013의 번호는 재사용하지 않는다. 기존 V010은 수정하지 않는다. 새 브로커나 Spring Batch 의존성은 추가하지 않는다.
- 회수 기능 제외에 따라 `TICKET_REVOKED` 작업은 등록하지 않는다. 이번 호환 수정은 최신 GD-93 초기 SQL을 기준으로 하며, 이미 적용한 DB의 체크섬 충돌·데이터 전환·Flyway repair는 별도 확인이 필요하다. 실제 DB 초기화나 데이터 삭제는 수행하지 않는다.
- payload의 발표 ID에는 DB 외래 키가 없으므로 발표의 존재·실제 공개 여부는 작업을 등록하는 업무 담당자가 검증한다. 알림 워커가 발표 상태를 변경하거나 새 공개 계약을 정하지 않는다.

## 처리와 재시도

- 작업 선점과 사용자별 생성은 짧은 별도 트랜잭션이다. 사용자 알림과 처리 위치를 함께 저장하며, 중간 실패 시 이미 생성된 알림은 보존한다.
- `occurrence_key`와 `(job_id, user_id)`의 기존 UNIQUE 제약으로 중복을 막는다. 이미 생성된 알림의 ID·문구·생성 시각·읽음·발송 결과를 덮어쓰지 않는다.
- 2026-10-01 사용자 확인 기준: 생성·모의 발송 각각 최초 1회와 최대 3회 재시도, 간격은 10초·30초·60초다. 일시적 DB 접근·연결 오류와 모의 발송 일시 실패만 자동 재시도한다. 입력·제약 오류 등은 최종 실패로 남긴다.
- 생성 실패는 `notification_jobs.last_error`, 발송 실패는 `notifications.last_delivery_error`에 안전한 오류 코드만 기록한다. 예외 원문·SQL·사용자 문구는 실패 필드에 저장하지 않는다.
- 실패 WARN 로그에는 작업 또는 알림 ID·시도 차수·예외 클래스만 남긴다. 예외 메시지·스택·알림 문구·수신자 정보는 출력하지 않는다.
- 선점 횟수 소진으로 최종 실패 처리할 때는 기존 오류 코드를 보존한다. 기록된 오류가 없으면 일시적 처리 실패 코드 `NOTIFICATION-005`를 남긴다.
- 선점 제한 시간은 60초다. 생성은 사용자별 저장 시 연장한다. 장애로 선점이 만료되면 다음 처리자가 차수를 올려 이어 처리한다. 만료된 4번째 시도도 최종 실패로 전환해 무한 반복을 막는다.
- 생성이 모두 끝난 뒤 완료 기록이 제한 시간을 넘더라도 재선점되지 않았다면 완료로 확정한다. 재선점 후에는 이전 차수의 완료·실패 기록을 차단한다. 사용자별 알림 생성 시에는 기존대로 유효한 선점을 검사한다.
- 선점 조회에서 시도 횟수를 소진한 항목은 최종 실패로 전환하고 다음 후보를 확인한다. 해당 항목 때문에 뒤의 실행 가능한 생성·발송 처리가 다음 폴링까지 미뤄지지 않는다.
- 모의 발송은 `next_delivery_attempt_at`을 선점 제한 시각으로도 사용한다. 성공 시 비우고 실패 시 재시도 시각 또는 null을 저장한다. 선점 차수를 함께 검사하므로 이전 처리자의 늦은 결과가 새 결과를 덮어쓰지 못한다.
- 모의 발송이 60초를 넘더라도 다른 처리자가 재선점하지 않았다면 성공 결과를 저장한다. 재선점 후에는 이전 차수의 성공·실패 결과를 저장하지 않는다.
- 모의 발송 성공은 `SENT`·발송 시각만 기록한다. 읽음 여부는 사용자 API만 변경한다. 2026-10-23 사용자 확인으로 모의 발송기는 기본 20% 확률로 `FAILED`, 80% 확률로 `SENT`를 반환한다. 실제 문자·메일·푸시 전송은 하지 않는다.
- `getddo.notification.mock.failure-percent`는 0~100 정수이고 기본값은 `20`이다. 최초·자동 재시도·관리자 복구 후의 각 발송 시도에서 새 난수를 뽑는다. 100건 중 정확히 20건을 고정 실패시키거나 특정 사용자를 계속 실패시키는 방식이 아니다. 범위를 벗어난 설정은 기동 시 거절한다.
- 발송기가 `FAILED`를 반환하면 기존 Service가 `NOTIFICATION-005` 일시 실패로 저장해 10초·30초·60초 자동 재시도를 예약한다. 4번째까지 실패하면 다음 시각을 비우고 관리자 발송 복구 대상으로 남긴다. 생성 완료와 기존 알림 ID·내용·읽음은 보존한다.
- 일반 API·DB 통합 테스트는 테스트 리소스에서 실패율을 `0`으로 설정해 성공 시나리오의 무작위 실패를 막는다. 실패 경로는 전용 테스트의 `100` 설정과 고정 난수로 검사한다. 기존 실패·재시도 검증은 유지하며 테스트를 비활성화하지 않는다.
- 발표용 최종 실패를 확실히 보여줄 때는 격리 실행 환경에서 `100` 설정으로 재현한다. 기본 20%에서는 네 번 연속 실패할 이론 확률이 0.16%여서 모든 발표 실행에 최종 실패가 생기는 것은 아니다. 이 작업은 서버 설정·공유 DB·배포를 변경하지 않았다.

## 이벤트 시작 작업 등록 — GD-69

- `EventStartNotificationService`는 기존 `events.starts_at`을 조회하므로 이벤트 생성 시 별도의 예약 테이블이나 사용자 목록을 저장하지 않는다. 이벤트·사용자 업무 코드와 스키마는 변경하지 않는다.
- 폴링 당시 시작 전 10분 구간에 들어온 미삭제 `SCHEDULED` 이벤트를 하나씩 선택한다. 2026-10-09 사용자 확인에 따라 10분 전을 놓쳤어도 시작 전이면 등록하며, 시작 시각 이후에는 새로운 시작 작업을 등록하지 않는다.
- 이벤트 행 잠금과 작업 등록을 같은 트랜잭션으로 처리한다. 다른 처리자가 잠근 이벤트는 `SKIP LOCKED`로 건너뛰어 동시 처리를 줄인다. 중지되지 않은 `EVENT_START` 작업이나 이미 생성된 시작 알림이 있으면 후보에서 제외한다. 발생 키는 `event-start:<이벤트 UUID>:<시작 시각 UTC>`이며 시각은 마이크로초로 정규화한다. 기존 발생 키의 작업도 동일하게 조회하므로 배포 전에 등록한 시작 작업을 중복 생성하지 않는다.
- `NOT EXISTS`가 이벤트 행 잠금 획득 전에 읽은 뷰에서는 다른 처리자가 커밋한 작업을 보지 못해 재등록을 시도할 수 있다. 최종 작업 중복 방지는 `occurrence_key` UNIQUE와 멱등 등록이 담당한다. 같은 payload는 기존 작업 ID를 반환하고 다른 payload는 `OCCURRENCE_CONFLICT`(`NOTIFICATION-004`)로 거절해 트랜잭션을 롤백한다. 등록 실패 WARN이 발생할 수 있지만 기존 작업을 덮어쓰거나 중복 작업 행을 만들지는 않는다.
- 알림 생성 처리를 시작하는 이 단계에서 현재 최소 멤버십 이상의 `ACTIVE`·`USER` ID 목록을 조회하고 payload에 저장한다. 활성 일반 사용자만 대상으로 하는 기준은 2026-10-09 사용자 확인을 받았다. 이후 사용자별 저장·재시도에서는 이 목록을 유지한다. 사용자별 저장 직전에 매번 자격을 재조회하지 않는다.
- 예약 시각은 시작 10분 전이며, 링크는 현재 프론트엔드 이벤트 상세 경로인 `/events/<이벤트 UUID>`다. 대상이 없는 작업도 등록·완료해 반복 폴링에서 같은 이벤트를 계속 선택하지 않게 한다.
- 시작 작업 등록이 실패하면 트랜잭션을 롤백하고 다음 폴링에서 다시 조회한다. WARN에는 예외 유형만 남기며 기존 작업 생성·모의 발송 단계는 계속 실행한다.
- 이미 등록한 작업은 기존 GD-68 재시도 흐름으로 처리한다. 작업 적체나 장애가 있으면 사용자별 저장이 늦어질 수 있으며, 이미 등록한 작업을 시작 시각 이후에 자동 폐기하지 않는다. GD-70 서비스가 호출되면 예전 시작 작업의 남은 생성을 막는다. 실제 이벤트 수정·취소 업무의 호출 연결은 아직 구현하지 않았다.

## 일정 변경·취소 안내 — GD-70

- 상태: 알림 기능 구현 / 이벤트 담당자 호출 연결 대기 / 2026-10-11 사용자 로컬 빌드 성공 확인.
- 내부 진입점은 `EventChangeNotificationService.register(EventNotificationChange)`다. 공개 HTTP API나 이벤트·응모권 업무 코드는 추가하지 않는다.
- 이벤트 담당자는 이벤트 행을 잠그고 허용 여부를 검증한 뒤, 일정 저장 또는 취소·반환 처리를 수행하는 **동일 Service 트랜잭션 안에서** 호출한다. 별도 비동기 호출이나 커밋 이후 콜백으로 작업 등록을 분리하지 않는다. 사용자별 알림 생성·모의 발송은 기존 워커가 비동기로 처리한다.
- 일정 변경 입력은 `EventNotificationChange.scheduleChanged(changeId, eventId, title, previousStartsAt, startsAt, occurredAt)`다. 취소 입력은 `EventNotificationChange.canceled(changeId, eventId, title, occurredAt)`다.
- `changeId`는 이벤트 담당자가 해당 변경·취소 건에 부여하고 재시도에 재사용할 UUID다. `occurredAt`도 최초 발생 시각을 유지한다. 재시도마다 새 UUID나 현재 시각을 만들어 전달하면 같은 발생 건으로 처리할 수 없다. 변경 ID·원본 발생 입력의 보존 방식은 이벤트 담당자와 연결 전에 합의한다.
- 알림 서비스는 이벤트 행 잠금으로 시작 생산자와 직렬화하고, 저장된 제목·상태·변경된 시작 시각을 확인한다. 이벤트 상태·일정·반환 자체는 변경하지 않는다. 같은 발생 키의 재요청은 저장된 입력을 최신 잠금 읽기로 비교하고 최초 수신자를 재계산하지 않는다.
- 예전 시작 작업의 `payload.generationStoppedBy`에 중지 원인 발생 키를 저장하고 선점을 해제한다. 작업·기존 알림을 삭제하거나 기존 성공·실패 상태를 덮어쓰지 않는다. 이 필드가 있으면 선점, 사용자별 생성, 늦은 완료·실패 기록 모두 막는다. 상태가 `PENDING` 또는 `PROCESSING`이어도 중지된 작업은 실행 대상이 아니다. GD-72 관리자 조회·재처리는 이 필드도 확인해야 한다.
- 시작 알림 수신자는 `notifications`에 실제 생성된 `EVENT_START` 알림의 사용자다. 모의 발송 성공·읽음 여부나 변경 시점의 멤버십으로 다시 필터링하지 않는다. 시작 작업을 먼저 잠가 향후 INSERT를 막은 다음, 현재 읽기로 수신자를 고정하므로 부분 생성 중 변경도 처리한다.
- 아무에게도 시작 알림이 생성되지 않은 일정 변경은 새 일정의 10분 전 구간에서 시작 생산자가 현재 자격으로 새 작업을 등록한다. 이미 받은 사람이 있으면 시작 알림을 재발송하지 않고 변경 안내만 생성한다. 취소 시 새로운 시작 작업은 생성하지 않는다.
- 안내 작업의 발생 키는 `event-change:<변경 UUID>`다. 수신자가 없어도 빈 작업을 기록한다. 기존 `source_job_id`에 가장 최근 시작 작업을 연결하고 수신자 목록은 안내 payload에 고정한다. 새 컬럼·Flyway 변경은 없다.
- 기존 시작 알림의 문구·읽음·모의 발송 상태를 바꾸지 않는다. 별도 변경 안내에는 이전·새 시작 시각을 한국 시간으로 표시하며 이벤트 링크를 포함한다.
- 롤백, 부분 생성 중 변경, 취소, 재요청 충돌, 동시 등록 및 이전 스냅샷 회귀 테스트를 추가했다. 2026-10-11 사용자가 최신 dev 반영 후 `./gradlew build` 성공을 확인했다. 에이전트는 사용자 요청에 따라 테스트·빌드를 직접 실행하지 않았다.

### 담당자 연결 시 확인할 항목

1. 이벤트 수정 담당자와 변경 ID·최초 발생 입력 보존 및 같은 트랜잭션 호출 위치를 확인한다.
2. 취소·반환 담당자와 취소·반환 성공에만 알림 작업이 함께 커밋되도록 연결한다.
3. 실제 수정·취소 API 통합 테스트로 실패 시 원본 업무와 알림의 롤백을 확인한다. 현재 알림 통합 테스트는 트랜잭션 안의 JDBC 변경으로 이 경계를 검증한다.
4. GD-61 삭제는 2026-10-13 사용자 확인에 따라 이벤트 논리 삭제를 flush한 같은 트랜잭션에서 `EventChangeNotificationService.stopForDeletedEvent(eventId)`를 호출한다. 저장된 삭제 여부를 확인한 뒤 기존 시작 작업에 `event-deleted:<이벤트 UUID>` 중지 근거를 기록한다. 이미 생성된 알림·작업 이력을 보존하고 추가 시작 알림 생성만 막으며, 별도 삭제 안내는 등록하지 않는다. 중지 실패 시 삭제도 롤백한다. 실제 처리 흐름은 [이벤트 삭제](../02-api/event-deletion.md)를 참고한다.

## 장애 확인

이벤트 연결 알림의 사용자별 생성은 이벤트 공유 잠금 → 알림 작업 쓰기 잠금 순서다. 이벤트 삭제·일정 변경과 같은 부모 이벤트 → 작업 순서를 유지한다. 작업을 먼저 잠근 뒤 알림 INSERT의 이벤트 FK 검사에 맡기는 순서로 바꾸면 이벤트 삭제와 교착할 수 있다.

1. DB 연결과 워커 실행 여부를 확인한다. DB 접근·실패 기록 자체가 불가능한 동안에는 저장된 선점의 만료 후 처리가 복구된다.
2. 생성·발송의 상태와 차수·다음 시각·안전한 오류 코드를 확인한다. 아래 조회에 알림 내용이나 개인정보는 포함하지 않는다.

```sql
SELECT HEX(id), status, attempt_count, scheduled_at,
       JSON_UNQUOTE(JSON_EXTRACT(payload, '$.generationStoppedBy')) AS generation_stopped_by,
       next_attempt_at, lease_until, last_error
FROM notification_jobs
WHERE status IN ('PENDING', 'PROCESSING', 'FAILED');

SELECT HEX(id), mock_delivery_status, delivery_attempt_count,
       next_delivery_attempt_at, last_delivery_error
FROM notifications
WHERE mock_delivery_status IN ('PENDING', 'FAILED');
```

3. 최종 실패는 자동 재시도하지 않는다. 저장된 오류 코드와 안전한 WARN 로그를 확인하고 입력·연결·원본 참조 등의 원인을 먼저 확인한다.

### 최종 실패의 관리자 복구 — GD-72

- 활성 ADMIN 사용자 문맥을 사용해 AN01~AN05를 호출한다. 확정 경로·필터·응답·오류는 [공용 알림 API](https://github.com/GETDDO/getddo-spec/blob/main/05-api/notification.md#관리자-알림-운영--an01an05-확정)를 따른다.
- 작업 목록·상세와 사용자별 모의 발송 이력을 조회한다. createdAt DESC, id DESC의 페이지이며 생성 시각 [from,to)로 검색한다. 목록 조회는 읽음 상태를 바꾸지 않는다.
- AN04·AN05의 `userName`은 `NotificationAdminRepositoryImpl`이 `notifications.user_id`와 `users.id`를 조인해 읽는다. 이름을 원본 알림에 저장하지 않는다. 목록의 필터·개수·정렬은 기존 알림을 기준으로 유지하고, 복구 조회는 `FOR UPDATE OF n` / `FOR SHARE OF n`으로 알림 행만 잠근다. 이 계약은 [관리자 알림 이름 필드](https://github.com/Uplus-GETDDO/getddo-spec/blob/main/05-api/notification.md#2026-10-21-관리자-알림-수신자-이름-추가)를 따른다.
- 생성 FAILED와 모의 발송 FAILED의 최종 실패만 복구한다. 다음 자동 재시도가 있거나 진행·성공 상태면 NOTIFICATION-010(409)으로 거절한다. 이미 접수한 같은 대상의 반복 요청도 409다.
- generationStoppedBy가 있는 생성 작업은 상태와 관계없이 복구하지 않는다. EVENT_START는 미삭제·SCHEDULED·시작 전인 이벤트만 생성 복구한다. 이미 생성된 사용자 알림의 모의 발송에 이 제한을 확대하지 않는다.
- POST는 202로 접수 결과를 반환하며 실제 성공을 보장하지 않는다. 기존 워커가 처리하고 기존 발생 키·수신자·내용·알림 ID·읽음 상태를 보존한다.
- 최초 시도와 최대 3회 자동 재시도로 구성된 새 복구 구간을 시작한다. 일시적인 장애만 자동 재시도하고 잘못된 입력·제약 오류는 즉시 최종 실패다. 기존 10초·30초·60초 간격을 유지한다.
- V021의 attempt_base·delivery_attempt_base에 복구 시점 누적 차수를 보관한다. 워커의 누적 차수는 계속 증가하고 해당 구간 시도 횟수만 차이로 계산한다. 늦은 갱신은 두 차수를 모두 검사한다. 내부 결정과 대안은 [ADR-0005](../04-decisions/0005-notification-manual-retry-fencing.md)를 참고한다.
- 공통 AuditLogService로 접수 관리자·대상·전후 상태·차수를 기록한다. 감사 저장 실패 시 복구 접수도 롤백한다. 조회와 거절된 요청에 별도 감사 기록을 추가하지 않는다.
- PENDING/PROCESSING/FAILED 상태·시도 횟수를 직접 수정하는 SQL을 지원 복구 절차로 사용하지 않는다.

### GD-72 배포 및 검증

- GD-87/GD-138의 추첨 V019와 번호 충돌을 피하도록 사용자 요청으로 알림 파일명을 V019에서 V021로 변경했다. SQL 내용은 유지했다. 배포 전 `flyway_schema_history.script`에서 이전 알림 파일 적용 여부를 확인한다. 이미 알림용 V019를 적용한 공유 DB에는 같은 컬럼을 추가하는 V021을 그대로 실행하지 않고 인프라 담당자와 적용 이력을 조율한다. 이번 변경은 DB 이력·데이터를 수정하지 않는다.

1. 이벤트 조회 PR #16이 병합되어 V017도 포함된다. 현재 DB의 Flyway 적용 이력을 확인하고 V017·V018·V021 적용 순서를 인프라 담당자와 맞춘다. 늦은 이전 버전 추가를 위해 기존 마이그레이션 수정·DB 초기화·임의 repair를 수행하지 않는다.
2. V021과 새 워커 코드를 전체 실행 인스턴스에 적용한 뒤 관리자 수동 복구를 사용한다. 인프라 담당자는 각 인스턴스의 배포 커밋을 확인하고 구버전 실행 인스턴스가 남아 있지 않은지 확인한다. 구버전 워커는 기준 차수 검사를 하지 않는다.
   - 롤백이 필요하면 관리자 복구 요청을 차단하고 전체 알림 워커 인스턴스를 중지한다. 진행 중 처리·늦은 콜백이 종료된 것을 확인하기 전에는 구버전 워커를 시작하지 않는다.
   - 복구 접수가 한 번이라도 있었다면 새 기준 차수 검사를 포함한 버전으로 복구한다. 구버전 워커와 수동 복구를 혼용하지 않으며, V021 컬럼 삭제나 누적 차수 초기화를 롤백 수단으로 사용하지 않는다.
3. 활성 ADMIN의 X-User-ID·X-User-Role로 목록·상세·필터와 202 접수/409 불가 응답을 확인한다. 시연용 헤더는 신원 인증 대체가 아니다.
4. 회귀 테스트에는 새 복구 구간의 4회 한도, 생성 중복 방지, 발송 복구 직후 새 선점 전의 예전 콜백, 동시 접수, 접수·감사 롤백을 포함했다. 사용자가 로컬 테스트 통과를 확인했고 병합 커밋 2a4aaef의 GitHub 빌드·테스트도 성공했다. 이후 리뷰 보강 커밋의 실행 결과는 PR #52 최신 CI에서 별도로 확인한다.

## 적용 범위와 한계

- DB 선점은 여러 서버의 동시 처리와 프로세스 종료 후 복구를 지원한다. 외부 발송은 수행하지 않으므로 외부 시스템과의 발송 exactly-once 계약은 만들지 않는다.
- 각 생성 작업의 수신자 목록은 한 번에 읽고 사용자별로 저장한다. 대규모 수신자에서 목록 저장·조회 및 재시도 비용은 별도 성능 측정이 필요하다.
- 이벤트 시작 생산자는 GD-69에서 연결한다. GD-70 변경·취소 알림의 실제 업무 호출 연결과 GD-71 결과 발표 생산자 연결은 후속 범위다. 공동 업무 코드와 공개 API는 변경하지 않는다.
- 시작 후보 조회에는 이벤트 전용 인덱스를 추가하지 않았다. 이벤트 데이터가 많아지면 후보 조회 시간과 행 잠금 범위를 측정하고 이벤트 담당자와 인덱스 변경 범위를 확인해야 한다.
