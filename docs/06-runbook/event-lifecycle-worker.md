# 이벤트 모집 상태 워커 확인 — GD-203

- 상태: 검토 대기 — 담당자 확인 전
- 구현·트랜잭션: [이벤트 상태 전환과 감사 기록](../02-api/event-lifecycle-and-audit.md)

## 설정과 정상 동작

- `getddo.event.lifecycle-worker.enabled`: 기본 true. false이면 워커를 생성하지 않는다.
- `getddo.event.lifecycle-worker.poll-delay`: 1 이상의 밀리초 숫자, 기본 1000ms. 이전 폴링 완료 후 다음 실행까지의 간격이며 잘못된 값은 기동 시 거절한다.
- `event-lifecycle-` 접두사의 전용 스레드 하나에서 실행한다. 첫 폴링은 기동 직후 시작한다. 공용 스케줄러 Bean이나 알림·추첨의 실행 설정은 바꾸지 않는다.
- 폴링당 최대 20개 후보를 순회한다. 처리 시각은 저장된 시각과 같은 UTC 기준이며 정각부터 전환 대상이다.
- 삭제되지 않은 `SCHEDULED`·`OPEN` 후보를 잠금 없이 읽고 한 이벤트씩 별도 트랜잭션에서 선점한다. 다른 워커나 업무가 잠근 이벤트는 건너뛴다. 선점 후 최신 상태를 재검사해 중복 변경을 막는다.
- 후보는 마지막 ID 뒤부터 순환하므로 반복 실패 이벤트만 있는 첫 묶음이 다음 이벤트를 계속 가리지 않는다. 커서는 인스턴스 메모리에 있으며 재시작 시 초기화된다. V027의 시작·마감 기한 인덱스를 적용해야 한다.

상태 반영은 비동기이므로 정확히 시작·마감 시각에 응답이 바뀐다고 보장하지 않는다. 기존 응모·수정의 서버 시각 검증은 계속 적용된다. 모집 상태 전환은 자동 추첨·수동 발표와 별개다.

## 종료

종료 신호를 받으면 새 폴링을 막고 진행 중인 폴링이 끝나기를 최대 30초 기다린다. 대기 시간을 넘겨도 진행 중인 트랜잭션을 강제로 중단하지 않는다. 종료 직전 이미 진입한 폴링은 기존의 최대 20개 후보 순회를 마칠 수 있다. 이벤트별 상태·감사 원자성을 유지하며, 미처리 이벤트는 재기동 후 다시 조회한다.

## 실패와 복구

`Event lifecycle deferred: eventId=..., failureType=...`는 해당 이벤트의 상태·감사 트랜잭션 실패다. 그 이벤트만 롤백하고 다음 후보는 계속 처리한다. 다른 이벤트의 성공은 취소하지 않는다. 순환 중 다시 도달하면 재시도한다.

`Event lifecycle update deferred: failureType=...`는 후보 조회 등 폴링 전체에서 발생한 오류다. 다음 폴링에서 다시 후보를 읽는다. 공통 DB·감사 저장소 전체 장애는 이벤트별 트랜잭션으로 해결되지 않으므로 연결과 공통 저장 기능을 복구해야 한다.

상태 지연이 지속되면 워커 활성화 여부, `event-lifecycle-` 전용 스레드 실행, DB 연결·장기 트랜잭션, 감사 저장 오류를 확인한다. 원인을 해결하면 다음 폴링에서 경과한 시각을 반영한다. 서버 중단 중 모집이 전부 끝난 SCHEDULED도 CLOSED로 복구한다. 감사 행을 임의 삭제하거나 상태를 수동 덮어써 복구하지 않는다.

마감 +1분이 지나도 추첨이 실행되지 않으면 모집 상태 확인 후 [추첨 실행 복구](draw-execution-recovery.md)를 따른다. 결과 공개는 관리자 수동 요청 대상이며 이 워커가 자동으로 공개하지 않는다.
